# JD 맞춤 포트폴리오

JD가 요구하는 채용 신호를 실제 경력 증거에 연결하고, 하나의 기본 포트폴리오를 회사·직무별 링크로 맞춤 편집해 최종 링크를 전달한다.

JD 분석이나 사이트 수정 전에 [출력 템플릿](references/output-templates.md)을 끝까지 읽고 형식을 준수한다.
회사별 DB 저장, 버전, 발행 또는 링크 관리 작업을 할 때는 [데이터와 링크 관리](references/data-and-links.md)를 끝까지 읽는다.

## 4단계 실행 계약

입력과 출처 감사는 준비 단계이며, 아래 네 단계를 순서대로 완료한다.

1. `JD 분석`: 핵심 역량, Pain Point, 우선순위 키워드, 필요한 증거를 정의한다.
2. `역량 구조화`: 경력을 CAR 구조로 정리하고 JD 역량과 검증 경험을 1:1로 매칭한다.
3. `콘텐츠 설계`: Hero 카피 3안을 만들고 근거와 5초 명확성을 비교해 최종안을 선택한다.
4. `웹사이트화·링크 발급`: 선택된 콘텐츠를 실제 Hero와 맞춤 페이지에 반영하고, 검증·저장·발행 후 접근 가능한 링크를 전달한다.

각 단계 결과를 다음 단계의 입력으로 사용한다. 사용자가 한 번에 전체 제작을 요청하면 중간 승인을 기다리지 않고 네 단계를 이어서 수행하되, 주장 자체를 바꿀 핵심 근거가 없으면 질문하거나 발행을 보류한다. 사용자가 중간 수정을 요청하면 같은 지원 건의 새 revision으로 저장하고 동일 링크에 반영한다.

## 필수 원칙

- `JD 분석 → 역량 구조화·증거 매칭 → 콘텐츠 설계 → 웹사이트화·링크 발급` 순서를 생략하지 않는다.
- JD를 요약하는 데 그치지 말고 회사가 채용으로 해결하려는 문제와 먼저 확인할 역량 신호를 해석한다.
- 이력서, 기존 포트폴리오, 프로젝트 설명, 사용자가 확인한 답변만 사실의 근거로 사용한다.
- 저장소에 이미 있는 문구라도 사용자가 본인의 자료라고 확인하지 않았으면 경력 근거로 사용하지 않는다.
- 템플릿에서 가져온 이름, 회사, 역할, 수치, 추천사, 링크는 디자인 참고 자료일 뿐이며 사용자의 경험으로 해석하지 않는다.
- 성과, 수치, 기간, 역할, 사용 도구를 추측하거나 만들어내지 않는다. 근거가 없으면 `[확인 필요]`로 표시한다.
- JD 문구와 사용자 경력을 구분한다. 해석은 `추론`으로 명시하고 확정 사실처럼 쓰지 않는다.
- 기본 `/` 포트폴리오를 보존한다. 사용자가 명시하지 않으면 회사별 맞춤 페이지 때문에 공통 원본을 덮어쓰지 않는다.

## 준비. 입력과 기준 자료 확인

1. JD 원문 또는 JD 링크를 확보한다. 링크를 받으면 현재 원문을 읽고 회사, 직무, 팀, 요구 경력, 책임, 우대사항을 구분한다.
2. 저장소의 현재 포트폴리오 문구와 프로젝트를 확인하되 먼저 출처 등급을 분류한다.
3. 사용자가 제공한 이력서·경력기술서·프로젝트 자료를 기준 자료로 삼는다.
4. 회사명, 직무명, 지원 링크 slug가 없으면 JD에서 안전하게 제안한다.
5. 자료가 부족해도 가능한 범위까지 진행한다. 주장 자체가 달라질 정도의 빈칸만 묶어서 질문한다.

### 출처 등급

- `검증됨`: 사용자가 본인의 경력이라고 명시했거나 사용자가 제공한 원본 자료에 존재하는 사실. 포트폴리오에 사용 가능하다.
- `미검증`: 저장소에 있으나 소유·정확성이 확인되지 않은 내용. 확인 전에는 포트폴리오 주장으로 사용하지 않는다.
- `템플릿`: 예시 인물, 회사, 수치, 추천사, 연락처를 포함한 샘플 콘텐츠. 디자인 구조만 참고하고 경력 증거에서 완전히 제외한다.
- `JD`: 회사가 요구하는 내용. 사용자의 보유 역량으로 바꾸지 않는다.
- `추론`: JD 또는 검증된 사실에서 도출한 해석. 추론임을 표시한다.

검증된 경력 자료가 하나도 없으면 JD 분석까지만 확정하고, 역량 구조화 표는 빈 증거 슬롯과 필요한 질문으로 작성한다. 템플릿 데이터를 채워 넣지 말고 실제 사이트 수정은 보류한다.

## Step 1. JD 분석

반드시 편집 전에 다음을 완성한다.

1. 직무 핵심 역량 Top 3~5를 우선순위로 추출한다.
2. 회사가 채용으로 해결하려는 핵심 Pain Point 1~2개를 해석한다.
3. 포트폴리오 전반에서 자연스럽게 반복할 우선순위 키워드를 정한다.
4. 각 역량을 검증할 증거 유형을 정의한다. 예: 성과 수치, 프로젝트 사례, 협업 경험, 문제 해결 방식.
5. 각 역량마다 JD 문장 근거, 숨은 의도 해석, 포트폴리오용 키워드, 필요한 증거 유형을 표로 작성한다.

짧은 JD 문구만 직접 인용하고, 나머지는 정확히 요약한다. 근거가 약한 해석에는 신뢰도를 표시한다.

## Step 2A. 역량 구조화

JD 분석 직후, 사이트를 수정하기 전에 모든 후보 경험을 경험 인벤토리로 재구성한다.

각 경험을 다음 순서로 정리한다.

1. 경험명
2. 프로젝트·업무의 맥락
3. 해결하려던 문제 또는 목표(Challenge)
4. 사용자가 주도적으로 수행한 행동(Action)
5. 측정 가능한 결과 또는 변화(Result)
6. 사용한 도구 및 방식
7. 이 경험이 증명하는 핵심 역량 태그 2~4개
8. 포트폴리오에서 강조할 한 줄 포지셔닝
9. 근거의 강도 및 보강 필요 메모

### 작성 기준

- 연대기보다 문제 해결 구조를 우선한다.
- 가능하면 수치, 퍼센트, 전환율, 성장률, 기간, 규모처럼 검증 가능한 표현을 사용한다.
- 도구 이름만 나열하지 말고 무엇을 더 빠르게 또는 더 잘 해결했는지 맥락과 함께 설명한다.
- 하나의 경험이 여러 역량을 증명하더라도 반복 서술하지 말고 대표 역량과 보조 역량을 구분한다.
- 결과가 약한 경험도 버리지 말고 협업, 탐색, 실행, 리스크 관리 등 다른 역할의 증거가 되는지 판단한다.
- 각 경험의 `수치 충분 여부`, `과장 위험`, `모호한 표현`, `추가로 필요한 자료`를 보강 메모에 기록한다.

## Step 2B. JD와 경험 매칭

1. JD 핵심 역량별로 가장 강한 경험 1~2개를 연결한다.
2. 근거 강도를 `강함 / 보통 / 약함 / 없음`으로 평가하고 이유를 쓴다.
3. 중복되는 경험은 대표 사례 하나를 전면에 배치하고 나머지는 보조 근거로 사용한다.
4. 근거가 없는 JD 역량은 카피로 위장하지 말고 Gap으로 남긴다.
5. Hero, 소개, 프로젝트 순서, 프로젝트 제목, 성과 지표, 협업 설명, CTA에서 무엇을 바꿀지 수정 계획을 만든다.

## Step 3. 콘텐츠 설계

JD 분석과 역량 구조화 결과를 웹에서 5초 안에 이해할 수 있는 콘텐츠로 압축한다. 이 단계에서 포트폴리오 편집에 사용할 최종 카피를 결정한다.

### 입력

- Step 1의 JD 핵심 역량, Pain Point, 우선순위 키워드
- Step 2A의 경험 구조화 결과와 근거 강도
- Step 2B의 JD-경험 1:1 매칭 결과

검증된 경험과 수치만 사용한다. JD에 있는 표현이라도 사용자 경험으로 증명되지 않으면 성과처럼 서술하지 않는다.

### Hero 카피 3안

사이트를 수정하기 전에 반드시 서로 다른 관점의 Hero 카피 3안을 작성한다. 각 안은 정확히 다음 구조를 따른다.

- 헤드라인 1줄
- 서브카피 최대 2줄
- 강조 키워드 정확히 3개
- 연결된 JD 핵심 역량
- 근거가 되는 검증 경험

작성 원칙:

- 직함이나 자기소개보다 해결할 수 있는 문제와 기여 방식을 먼저 보여준다.
- 채용 담당자가 5초 안에 `어떤 문제를`, `어떤 검증된 역량이나 근거로`, `왜 이 포지션에서` 해결할 사람인지 이해할 수 있게 한다.
- `전략적`, `혁신적`, `탁월한`, `데이터 기반` 같은 추상어는 단독으로 쓰지 않는다. 검증된 행동, 성과 또는 역량과 함께 쓴다.
- 웹에서 훑어 읽을 수 있도록 문장을 짧게 쓴다.
- 전문적이고 명확한 어조를 사용하고, 과장된 광고 문구처럼 쓰지 않는다.
- 증거가 약한 수치나 JD 키워드를 억지로 삽입하지 않는다.
- 세 안은 같은 문장의 단순 변형이 아니라 서로 다른 문제 해결 포지셔닝을 보여준다.

### 최종안 선택

세 안을 `JD 적합도`, `검증 근거의 강도`, `5초 명확성`, `전문성과 비광고성` 기준으로 비교한다. 가장 강한 안을 추천하고 선택 이유를 짧게 설명한다. 사용자가 별도 선택을 요청하지 않았다면 추천안을 최종안으로 확정해 사이트에 적용한다.

근거가 부족해 설득력 있는 Hero를 만들 수 없으면 빈칸을 추측으로 채우지 말고 필요한 증거를 `보강 필요 메모`로 제시한다.

## Step 4. 웹사이트 Hero 적용과 회사별 링크 발급

분석·구조화·매칭 표가 완성된 뒤에만 편집한다.

1. 기존 회사별 variant 구조가 있으면 그 데이터와 route를 사용한다.
2. 구조가 없다면 `/`는 공통 원본으로 유지하고 `/p/{slug}` 형식의 데이터 기반 variant 구조를 먼저 만든다.
3. Hero에는 Step 3에서 확정한 역할 라벨, 헤드라인 1줄, 서브카피 최대 2줄, 강조 키워드 3개, CTA를 입력한다. 성과 지표는 검증된 경우에만 노출한다.
4. 데스크톱과 모바일에서 줄바꿈, 대비, 오버플로, CTA 동작을 확인하고 첫 화면만 읽어도 회사 Pain Point와 후보자의 검증된 해결 역량이 연결되게 한다.
5. 프로젝트는 JD 적합도와 증거 강도 순서로 재배치한다.
6. JD 키워드는 정확한 경력 근거가 있는 위치에서만 자연스럽게 반복한다.
7. 프로젝트 설명은 `맥락 → Challenge → Action → Result` 흐름을 유지한다.
8. 지원 건과 revision을 DB에 저장하고, 발행할 때 public-safe 콘텐츠만 publication 레코드로 복사한다.
9. 새 JD에는 새 링크를 만들고, 같은 지원 건의 수정에는 새 revision을 만들되 기존 링크를 유지한다.
10. 회사별 페이지에는 기본적으로 `noindex, nofollow`를 적용하고 추측하기 어려운 slug를 사용한다.
11. 사용자가 요청하지 않은 개인정보, 내부 JD 분석, 다른 회사 지원 정보는 공개 응답이나 페이지 payload에 노출하지 않는다.
12. 배포 전에 저장소 루트의 `deploy.md`를 끝까지 읽고 현재 배포 기록을 작성한다.
13. 로컬 주소는 미리보기로만 취급한다. 최종 결과는 실제로 접근 가능한 발행 URL, revision, 상태를 확인한 뒤 전달한다.

### 필수 배포 게이트

다음 순서를 바꾸거나 생략하지 않는다.

1. 수정 전 화면을 모바일 `390px`, 태블릿 `768px`, 데스크톱 `1440px`에서 직접 검사한다.
2. 즉시 수정하기 전에 발견한 문제, 영향, 수정 방향을 `deploy.md`의 현재 배포 기록에 먼저 남기고 사용자에게 짧게 알린다.
3. 텍스트 오버플로, 이미지 잘림, 버튼 정렬, 카드 간격, 섹션 패딩, 가로 스크롤, 모바일에 남은 hover 동작을 포함해 발견한 문제를 직접 수정한다.
4. 빌드와 관련 테스트를 다시 실행하고 같은 세 너비에서 수정 항목과 전체 화면을 재검사한다.
5. 미해결 차단 문제가 없고 재검사를 통과한 경우에만 배포한다.
6. 배포 후 실제 URL을 같은 세 너비에서 다시 열어 route 새로고침, 콘텐츠 revision, CTA, 콘솔·네트워크 오류를 확인한다.
7. 최초 진단, 수정 내역, 재검사, 배포 후 확인 결과를 `deploy.md`에 모두 기록한다.

빌드 성공만으로 시각 검증을 통과한 것으로 간주하지 않는다. 수정 실패나 회귀가 있으면 현재 publication을 이전 revision에 유지하고 배포를 중단한다.

## 검증과 결과 보고

1. 변경 전후 문구가 동일한 사실을 표현하는지 검토한다.
2. JD 키워드만 늘고 근거가 약해진 문장이 없는지 확인한다.
3. 모든 수치와 고유명사를 기준 자료에서 역추적한다.
4. 프로젝트 빌드와 관련 테스트를 실행한다.
